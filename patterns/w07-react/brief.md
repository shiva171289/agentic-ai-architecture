# Brief — w07 react

**Topic:** ReAct loop — the model interleaves reasoning traces with tool calls, reads each observation, and decides the next step itself instead of following a code path you fixed in advance
**Date researched:** 2026-11-27
**Corpus:** `content/source-corpus/latest.md` (124 entries, window 7 days, keyword filter `react, agent, tool, reasoning, bedrock, agentcore, foundry, gpt`, regenerated 2026-11-27 07:07)
**Acme stage (W07):** ReAct loop decides when to call the order lookup tool before the reply
**Mapping focus:** Tool use runtimes

## Summary

ReAct is the first pattern in the ladder where control flow leaves your code: the model writes a reasoning trace, picks a tool, reads the result, and decides the next action, looping until it answers. The academic version of that idea is well established — ReAct (2210.03629) showed that interleaving reasoning and acting beats reasoning-only or acting-only baselines and makes trajectories readable; Toolformer (2302.04761), Gorilla (2305.15334) and ToolLLM (2307.16789) then isolated the hard part, which is not the loop but *tool selection and argument accuracy* at scale. What the current corpus adds is that the loop has moved from a prompt scaffold to a runtime and governance problem: AWS has put Bedrock Agents Classic into maintenance mode and points builders at AgentCore / the Strands Agents SDK for code-defined agents; Microsoft Foundry ships tool collections (Toolboxes) behind one MCP endpoint plus a preview tool policy; Google Cloud puts an inline policy engine in front of every proposed tool call, reporting attack success dropping from 48.7% to 0.9% on AgentDojo; LangChain's Tool Gateway makes credentials, scopes and traces part of the tool layer. For Acme, W07 is the small step of letting the agent decide *whether* it needs `get_order_status` before writing a reply — and the honest caution is that every governance capability arriving this month exists because an unchecked loop executes whatever it is talked into.

## Key concepts

- **ReAct = interleaved reason + act, and the paper is explicit about why.** ReAct (2210.03629) has the model "generate both reasoning traces and task-specific actions in an interleaved manner": reasoning traces "help the model induce, track, and update action plans as well as handle exceptions", while actions "interface with external sources ... to gather additional information". On HotpotQA and Fever it beats chain-of-thought by retrieving through a Wikipedia API instead of recalling facts; on ALFWorld and WebShop it beats imitation and RL baselines by 34% and 10% absolute success. The interpretability claim matters for support work: the trajectory is readable, so a human can see *why* the agent called a tool.
- **Anthropic's definitional line: an agent is the loop, a workflow is a fixed path.** "Workflows are systems where LLMs and tools are orchestrated through predefined code paths"; agents "dynamically direct their own processes and tool usage". Its one-sentence implementation: agents "are typically just LLMs using tools based on environmental feedback in a loop". That is the W07 boundary — W02 (chain) and W05 (orchestrator) fix the path; W07 does not.
- **Tool selection is a learned behaviour with an error rate, so budget it.** Toolformer (2302.04761) trains a model to "decide which APIs to call, when to call them, what arguments to pass, and how to best incorporate the results" from a handful of demonstrations per API. Gorilla (2305.15334) shows the failure mode plainly: models struggle to "generate accurate input arguments" and "hallucinate the wrong usage of an API call" — which is why it pairs the model with a document retriever so it "adapts to test-time document changes". ToolLLM (2307.16789) scales the same problem to 16,464 real REST APIs and needs an API retriever plus a search over candidate call chains. Three papers, one design rule: keep the tool set small, keep the descriptions current, and expect argument errors.
- **The loop is a runtime decision, not a prompt trick.** The Bedrock agents doc root now leads with a notice that Amazon Bedrock Agents is "now Amazon Bedrock Agents Classic", that you can no longer sign up, and that code-defined agents should be built with the Strands Agents SDK on AgentCore. AgentCore runtime instances went GA in AWS GovCloud (US-West) (corpus) with GPU/memory/compute-optimized instance types and agent sessions of up to 14 days. Long-running tool loops are being sold as a hosting property, not a prompting one.
- **Every tool-call step costs tokens you did not budget.** Anthropic's tool-use page counts tool-use overhead in three places — the `tools` parameter (names, descriptions, schemas) in every request, `tool_use` blocks in requests and responses, and `tool_result` blocks sent back — plus a per-model tool-use system prompt (about 286 tokens for current Opus/Sonnet/Haiku generations, higher on older ones). A five-step loop re-sends all of that five times.
- **Tool use is a governance surface first, a capability second.** Google Cloud now requires AI agents to reach Workspace through Workspace MCP servers or the Workspace CLI rather than the REST APIs, with "policy checks on every request" and enforcement starting 1 February 2027; its Agent Gateway "verifies Agent Identities against Agent Registry, enforces IAM policies and default-deny outbound rules, and screens requests with Model Armor". The companion Google Developers post puts an inline evaluator in front of execution: semantic governance policies "validate every proposed tool call against user intent and natural language constraints before execution", taking AgentDojo attack success from 48.7% to 0.9% on a Gemini 2.5 Flash agent.
- **Scope the loop's credentials down, don't inherit them.** AWS STS `GetScopedCredentials` exists because "you often want each agent or sub-agent to have only the permissions its tasks require, rather than the full permissions of the session that started it". LangChain's Tool Gateway does the same at the tool layer: a *tool kit* is "a curated set of tools published at a single URL" and "when connected to a specific tool kit, an agent only sees the tools bundled in it", with credentials, identity and a trace per call. Foundry's Toolboxes group tools "into a versioned collection behind one MCP endpoint" and a preview tool policy "centrally set[s] approved tool types, MCP endpoints, and connectors".
- **Agent-written code needs a sandbox, not a permission.** Lambda durable functions gained a developer preview that orchestrates Lambda MicroVMs — isolated VMs for "untrusted or agent-generated code", with checkpointing, retries and parallel MicroVM orchestration from SQS or EventBridge. This is the compute half of a tool loop that can run code.
- **Observability is aimed at tool misuse, not just latency.** Foundry Insights clusters production traces into findings such as "where an agent is failing, which tools it misuses, and where cost is concentrated", and multi-turn evaluation scores whole conversations (both GA). LangSmith's Agent Lake stores "every trace your agents produce"; Google's Agent Anomaly Detection (corpus) analyses OpenTelemetry traces and logs to flag "goal hijacks and tool misuse", catching 87% of harmful agent instructions across five public benchmarks.
- **Tool compliance is now a training target.** Google's multi-turn agentic RL post trains a tool-using agent with agentic GRPO to improve "complex reasoning and tool compliance in interactive environments" — i.e. following a tool's call contract is treated as a learned property, not a prompt.
- **Framework plumbing keeps moving under the loop.** LangGraph `1.2.24` (2026-11-20) fixed `REMOVE_ALL_MESSAGES` handling in the messages reducer and `None` checkpoints in `DeltaChannel`; the prebuilt package `1.1.3` fixed `wrap_tool_call` state overrides not reaching the tool. OpenAI's Agents SDK `v0.26.0` (2026-11-24) is a breaking minor: it requires input guardrails to stop queued function tools (use `run_in_parallel=False` to check before any tool starts), blocks local images in the experimental Codex tool unless the application approves them, and tightens Docker sandbox mounts. Both releases are loop-plumbing and safety fixes, not new loop features.
- **Tool infrastructure is being discovered and protected as a fleet asset.** AWS WAF can now discover LLM, MCP and A2A endpoints behind API Gateway, ALBs and CloudFront, flag an undocumented public-facing MCP server as a "shadow API", and protect endpoints with a managed rule group that calls Bedrock Guardrails for prompt-injection and jailbreak checks.

## Contrarian angles

1. **Most support replies still do not need a free-running loop.** Anthropic's own advice is to find the simplest solution and add complexity only when it demonstrably helps; its pattern material puts agents last, after five workflow patterns. The ReAct loop earns its keep only when the *next* step depends on what a tool returned and the number of steps is genuinely unknown. For "customer asks about an order", a fixed chain (W02) that always calls `get_order_status` is cheaper, testable and deterministic — and W08/W10 are already queued to formalise exactly that. Ship the loop only where the branch count is unbounded, and record the metric that forced it, the way W01's brief argued for the single augmented call.
2. **The loop is where prompt injection becomes action, and the fix belongs before execution.** Customers write the text the agent reads, and the agent has credentials for order and CRM tools. Google's inline policy check exists precisely because the previous model — "a valid OAuth token implied user intent" — fails once agents act at machine speed. The 48.7% → 0.9% result is a governance-mechanism number, not a quality number: without an intent check, a hijacked tool call looks like a successful step in the trace.
3. **"Thought / Action / Observation" text parsing is legacy scaffolding; the runtime returns structured calls.** Anthropic's API answers with `stop_reason: "tool_use"` and typed `tool_use` blocks that your code executes and returns as `tool_result`; Foundry and AgentCore expose the same shape, and Foundry's toolbox migration and LangGraph's `wrap_tool_call` fixes are plumbing for it. Hand-rolled trace parsing is where a loop silently degrades — it is a regex over a model's prose. Use the provider's tool contract and spend the effort on tool descriptions instead, which Anthropic calls out as its own discipline ("keep the format close to what the model has seen naturally occurring in text").
4. **Tool count is the loop's compounding cost.** Anthropic's overhead is per request, and Gorilla and ToolLLM both needed retrievers because argument accuracy degrades as the API surface grows. Adding a sixth tool raises every step's prompt cost and lowers selection accuracy; LangSmith's answer is to publish a curated kit so the agent "only sees the tools bundled in it", and Foundry's is a versioned toolbox behind one endpoint.

## Open questions

- **What stop rule ends the loop, and who owns it?** ReAct has no built-in terminator; nothing in the corpus or papers gives a max-step, token-budget or wall-clock number for a customer-facing loop. A wrong answer delivered after nine tool calls is worse than a fast, honest "I need to check that". The control must be ours, not the model's.
- **How do you evaluate a non-deterministic trajectory?** Foundry's multi-turn evaluation, Insights, LangSmith trace search and Hugging Face's agentic-evals post are all pointed at this, but no source states a pass threshold or a sampling rate for a tool loop, only that scoring whole conversations matters "because that is how most agents fail in practice".
- **Which runtime hosts the Acme loop?** AgentCore runtime instances (up to 14-day sessions) vs Lambda durable functions with checkpointing vs Foundry hosted agents — the corpus documents all three and compares none. This is the W07 mapping-focus gap, and W19/W23/W38 are the weeks that are supposed to settle it.
- **What does inline tool-call governance cost?** Google's semantic policies evaluate every proposed call before execution and AWS's WAF rule group bills Bedrock Guardrails per content-inspection call. Neither publishes the added latency per tool step, and it multiplies by the number of steps.
- **When does a tool loop make sense for the agent to decide, versus a router calling one fixed tool?** The corpus has no guidance on the Acme-shaped case: one tool, one branch. W09 (agent or workflow?) is scheduled to answer it in words rather than code — this brief should not pre-empt it with a claim.
- **Does the tool-use system-prompt overhead exist on every provider?** The Anthropic figures are model-specific and explicit; the corpus entries from AWS, Microsoft and Google do not publish comparable per-request overhead, so cross-provider cost comparison (W35) cannot be done from these sources yet.
